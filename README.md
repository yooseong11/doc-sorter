# doc-sorter (문서 분류기)

![문서 분류기 썸네일](./docs/portfolio-thumbnail.png)

소규모 회사 경영지원 담당자를 위한 문서 자동 분류 웹앱입니다. 업로드한 문서를 지정한 카테고리로 나누고, 사용자가 확인한 뒤 폴더에 저장하면서 CSV에 기록을 남깁니다.

## 기술 스택

| 영역 | 기술 |
|---|---|
| **Frontend** | React, Vite |
| **Backend** | Vercel Functions, Node.js |
| **AI** | OpenAI API, DeepSeek |
| **Storage** | File System API, idb-keyval (IndexedDB) |
| **Testing** | Node --test |
| **Deployment** | Vercel |

## 문제를 어떻게 정의했나요: 스토리 맵핑

![포스트잇으로 만든 사용자 스토리 맵](./docs/stroymMap.jpeg)

채용 공고에서 회의록 분류기 같은 도구가 필요하다는 내용을 봤습니다. 다만 공고만으로는 그게 왜 필요한지 알 수 없었습니다.

앞서 비개발자를 위한 회의록 추출기를 만든 적이 있습니다. 요약한 내용을 마크다운으로 복사하는 기능을 넣었는데 이는 노션에 붙여넣을 때를 대비해서였습니다. 해당 복사 내용은 원문 인용을 전부 들어가도록 했습니다. 그런데 회의가 끝나면 요약만 메일이나 슬랙으로 보내는 사람이 더 많다는 걸 개발을 마치고 나서야 깨달았습니다. 그탓에 원문 내용을 포함하지 않게 마크다운 형식으로 회의록 요약을 복사하는 기능을 뒤늦게야 추가했습니다. 

위와 같은 실수를 반복하고 싶지 않아서 문서 분류기는 시작할 때부터 사용자 요구사항을 분명히 해두기로 했습니다. 제프 패튼의 『사용자 스토리 맵 만들기』를 읽고 책에 나온 방법을 그대로 따라했습니다. 정호연이라는 가상 인물을 만들어, 경영지원팀에 휴무·세금 영수증·복지 관련 문서가 제목도 정리되지 않은 채 들어와 매일 분류하느라 시달리는 상황까지 적었습니다. 이 단계는 포스트잇을 붙여가며 손으로 했습니다 이후에는 AI와 함께 정리된 내용을 다듬었습니다.

덕분에 화면설계서가 전보다 훨씬 또렷해졌습니다. 릴리스를 3단계로 쪼갠 덕에 완성된 결과물을 일찍 볼 수 있었고, lib에 함수가 뒤엉키는 문제도 그때 발견해 리팩터링으로 정리했습니다.

## AI를 어떻게 사용했나요?

### ADR을 남겨서 버린 대안이 다시 올라오지 않게 했습니다

AI는 대화가 길어지면 맥락을 잊고 앞에서 버린 대안을 종종 다시 꺼내곤 합니다. 이때마다 매번 다시 AI에게 설명하는데 시간이 꽤 들었습니다. 나름 이런 상황을 방지하고자 한 대화에서 추론을 끝내고 그 결과를 이어 붙여 코드를 구현해봤지만, 프로젝트 초창기에 정한 정한 타깃 유저는 잊어버리고 카테고리를 늘리자는 말이 나왔습니다.

이러한 문제를 해결하기 위해 ADR 폴더를 만들고 결정·이유·버린 대안을 짧게 적었습니다. 개발 초기부터 진행중까지 아키텍쳐에 관련된 결정 사항이 적혀있기에 해당 폴더와 파일을 만들고 단 한 번도 AI가 엉뚱한 제안을 하지 않았습니다. 덕분에 이전과 달리 개발 시간과 토큰 사용량이 확실히 줄어들었습니다.

### 대화를 시작할 때 ADR은 제목만 읽게 했습니다

본문은 그 결정과 관련된 작업을 할 때만 읽게 해서 토큰을 아꼈습니다. ADR 문서 하나를 300자까지만 텍스트를 적으라고 명령했지만, 파일 수가 늘면 어쩔 수 없이 대화 초반에 사용하는 토큰은 계속 늘어납니다. ADR이 10개가 넘어갈 때 쯤에 제목만 읽히는 방법을 채택했습니다. 사용자 흐름은 이미 스토리 맵으로 통째로 읽히고 있으니 나머지 세부 사항은 필요할 때 꺼내 보면 된다고 판단했기 때문입니다. 해당 방법론을 채택한 이후에  lib 폴더의 함수를 리팩토링했습니다. 이때도 모든 ADR의 제목만 읽고 본문은 직접적으로 관여된 0017 ADR만 읽었는데도 문제없이 바이브 코딩을 진행할 수 있었습니다.

### 특정 AI에 종속되지 않는 개발 환경을 만들었습니다

Claude에서 작업하다 Codex로 넘어가도 에이전트가 로컬 파일과 스킬만으로 바로 맥락을 잡을 수 있게 했습니다.
ADR스킬과 더불어 `AGENTS.md`에 대화를 시작하면 무조건 `STORY_MAP.md`를 읽도록해서 사용자가 앱을 쓰는 흐름부터 파악하게 했습니다. (이때 `AGENTS.md`는 6줄로 줄여서 최대한 토큰 사용량을 줄였습니다) 해당 방법의 장점은 총 3가지가 있습니다.
첫째, 도구를 갈아타는 비용이 사라집니다.
둘째, 한 도구가 막혀도 작업을 멈추지 않을 수 있습니다.
셋째, 사람에게도 그대로 통합니다.
이러한 장점들 덕분에 해당 프로젝트의 첫 번째 릴리스 배포까지 2일 밖에 걸리지 않았습니다.
