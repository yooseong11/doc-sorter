# 0011. 저장 부분 실패와 기록 시점

- 상태: 채택
- 날짜: 2026-09-18

## 맥락
저장은 파일을 하나씩 폴더에 쓰는 반복문이다. 12개 중 5개를 쓴 뒤 권한 회수나 디스크 용량 부족으로 실패할 수 있다. File System Access API에는 트랜잭션이 없어서, 되돌리려면 이미 쓴 파일을 직접 지워야 한다.
[0006](0006-log-csv.md)은 기록표를 "같은 날 이어 쓰기"까지만 정했고, 언제 쓰는지는 정하지 않았다.

## 결정
- 이미 저장된 파일은 그대로 둔다. 되돌리지 않는다.
- 파일 하나를 쓸 때마다 기록표에 한 줄씩 이어 쓴다.
- 하나가 실패해도 반복문은 멈추지 않고 끝까지 돈다. 다 돈 뒤에 성공·실패 개수와 실패 사유를 보여주고, 재시도는 실패한 파일만 한다.

## 이유
- 되돌리기는 삭제 권한이 필요하다. 권한 회수로 실패한 경우엔 `removeEntry`도 실패해서 되돌리기 자체가 실패한다. 가장 흔한 실패 원인에서 작동하지 않는 방식이다.
- 남의 회사 폴더에서 앱이 파일을 지우는 동작은 틀렸을 때 비용이 크다. [0005](0005-filename-conflict.md)의 `_2` 규칙과 겹치면 방금 쓴 `연차_2.pdf`인지 원래 있던 파일인지 판단해야 하고, 잘못 지우면 휴지통 없이 사라진다.
- 성공분을 남기면 사용자가 할 일은 "실패한 7개 다시"로 끝난다. 되돌리면 12개를 처음부터 다시 해야 한다.
- 기록표를 배치 끝에 한 번에 쓰면, 중간에 탭이 닫히거나 저장이 멈췄을 때 이미 폴더에 들어간 5개가 기록표에 없다. 기록표는 "메일로 받은 그 파일 어디 갔지"를 찾는 표라서([0006](0006-log-csv.md)) 실제 폴더보다 적게 적히면 역할을 못 한다. 파일 단위로 쓰면 기록표와 폴더가 항상 일치한다.
- 실패한 파일은 애초에 줄을 쓰지 않으므로, 재시도해서 성공해도 줄이 두 번 남지 않는다.
- R1은 한 번에 수십 개 규모라, 파일마다 한 줄 이어 쓰는 비용이 문제되지 않는다.

## 버린 대안
- 되돌리기(롤백): 권한 회수 상황에서 작동하지 않고, 사용자 파일을 지우는 위험을 앱이 진다.
- 배치 완료 후 기록표 일괄 기록: 중단되면 폴더에는 있는데 기록표에는 없는 파일이 생긴다.
- 실패 시 즉시 중단: 나머지 파일이 되는지 안 되는지 알 수 없다. 용량 부족이면 어차피 다 실패하지만, 특정 파일만의 문제일 때 전부 멈춘다.

## 결과
- 파일별 상태가 필요하다. 분류 상태와 같은 모델을 쓴다([0013](0013-partial-classify-failure.md)).
- 기록표 쓰기 자체가 실패하면 파일은 이미 옮겨진 상태다. 이때는 화면에 경고만 띄우고 저장을 되돌리지 않는다.
- 부분 저장 후 폴더를 정리해 주는 기능: 보류.
