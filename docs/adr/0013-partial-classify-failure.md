# 0013. 분류 부분 실패와 파일 상태 모델

- 상태: 채택
- 날짜: 2026-09-18

## 맥락
분류는 파일 단위로 서버 API를 호출한다. 네트워크 오류, 타임아웃, 텍스트 추출 실패로 일부 파일만 실패할 수 있다. 전체를 다시 돌릴지 실패분만 다시 돌릴지에 따라 상태를 어디에 두는지가 갈린다.

## 결정
- 파일마다 상태를 둔다: `대기` → `읽는 중` → `분류 중` → `분류됨` / `실패`(사유 포함).
- 재시도는 `실패`인 파일만 한다. 이미 분류된 파일과 사용자가 확인 화면에서 고친 카테고리는 건드리지 않는다.

## 이유
- 전체 재분류는 사용자가 확인 화면에서 손으로 고친 카테고리를 날린다([0004](0004-confirm-screen.md)). 고친 걸 날리는 재시도 버튼은 누르기 무섭다.
- 분류는 API 호출이라 재분류가 곧 비용이다. 12개 중 2개 실패에 12개를 다시 보낼 이유가 없다.
- 실패 사유를 파일 옆에 적으면 사용자가 판단할 수 있다. "글자가 없는 pdf"는 다시 눌러도 안 되고(OCR은 보류), "네트워크 오류"는 다시 누르면 된다.
- 저장도 파일별 상태가 필요하다([0011](0011-partial-save-failure.md)). 분류와 저장이 같은 파일 객체의 상태 필드를 쓰면 화면은 목록 하나만 그리면 된다. 상태를 두 군데 두면 "분류는 됐는데 저장은 실패"를 표현하려고 조합이 늘어난다.

## 버린 대안
- 전체 재분류: 사용자가 고친 결과가 사라지고 비용이 배로 든다.
- 첫 실패에서 전체 중단: 1개 실패로 나머지 11개를 보지 못한다.
- 자동 재시도 N회: 보류. R1에서는 사용자가 버튼을 누르는 것으로 충분하고, 실패 사유를 보여주는 쪽이 먼저다.

## 결과
- 상태는 파일 객체 하나에 모은다. 분류 상태와 저장 상태를 따로 두지 않는다.
- 확인 화면(S2)은 실패한 파일도 목록에 남기고 사유와 재시도 버튼을 붙인다.
- 실패한 파일에 사용자가 드롭다운으로 카테고리를 직접 지정하면 `분류됨`으로 보고 저장한다.
